## ページ構造の観察と独立した実装方針

| 領域 | 観察できた構造 | 応用した抽象原則 | 当テンプレートの実装 |
| --- | --- | --- | --- |
| ナビゲーション | 機能・導入事例・資料などのコンバージョン動線 | 来訪者が目的に直行できる全体ナビ | Sticky Header + Page Anchor + Mobile Menu |
| ヒーロー | 短い大見出し、無料利用の誘導、製品イメージ | 価値→導線→製品理解の順 | オリジナルコピー + CTA + CSS製ダッシュボード |
| 信用の補強 | 導入規模や企業の紹介 | 社会的証明は実証可能なもののみ掲載 | **未検証の実績を出さず、デザイン原則を表示** |
| プロダクト構成 | プロジェクト管理とデジタル帳票を別文脈で紹介 | ジョブ別に機能のまとまりを示す | 2種のワークスペースカード |
| 機能説明 | 案件、工程、帳票、写真、チャット、承認などを順次説明 | 事前の抽象説明を、操作イメージで補強 | 6タブ + 切り替わる独自サンプル画面 |
| 導入効果 | 数字・事例と機能のつながりを訴求 | 数字がないときは因果を説明する | Pain cards / 「設計原則」4項目 |
| 利用シーン | 建設、不動産、製造など幅広い利用領域 | 想定利用者を絞り、ジョブで話す | 現場監督・協力会社・発注者の3想定シナリオ |
| ページ末尾 | FAQ、資料請求、導入CTA、フッター | 不安を解消して次の行動へ導く | FAQ + ページ内CTA + 出典フッター |

## 実務上の判断

### 採用すべきもの

- **視線誘導**: 課題→解決方法→実際のUI→使い方→次の行動
- **製品の視覚化**: スクリーンショットがなくても、原則を理解できる独立したHTMLデモ
- **情報の塊の区別**: 大きくても2つのサービス単位に整理し、各サービスを主要機能へ接続
- **Semantic Color**: ブランド背景（緑）、CTA（オレンジ）、状態（グリーン系）と役割を分ける
- **FAQ**: 入力不要で質問を開閉でき、離脱前の不安を減らす

### 採用しないもの

- KANNAの公式ロゴ、アプリのスクリーンショット、導入企業のロゴ
- 公式キャッチコピーの全文転載、特有の装飾アセット、商用サイトのHTML/CSS/JS
- 他社の企業実績・アプリレビュー・成果数値
- 根拠のない「導入社数」「削減率」や実際には動かない申し込みフォーム
- 建築現場向けUIとしての実用性が下がる過度な装飾・3D演出

## 現在のBuilding Scheduleへの示唆

1. **工程表のベースライン**: KANNAは2026-10-08に、過去の基準計画と現在の工程を重ねて比較する機能を発表した。これは「差分・変更履歴・後続工程への影響」を検証するうえで直接的な競合ベンチマークとなる。詳細な仕様・契約条件は必ず一次情報を参照。
2. **LPとプロダクトUIは違う**: 今回のヒーローやCTAを施工管理画面に移植する価値は低い。採用候補は意味を持つカラー、情報の塊、アクセスしやすい導線、タブの理解しやすさ。
3. **データに関する誇張は禁止**: Building Scheduleの現行公開版はLocalStorage利用。テンプレートでクラウドや共同編集を「実装済み」と見せることはできない。
4. **段階導入**: ユーザー5人に、①現場一覧、②工程調整、③変更通知の順で主要タスクをテストする。KPIは特定操作完了までの時間・エラー・再操作率で評価する。
